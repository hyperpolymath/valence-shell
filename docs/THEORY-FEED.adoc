== How to apply

. *Every new issue or PR in a feeder repo states what it feeds valence-shell* in one line, `Feeds valence-shell: <frontier id or issue>`, or `Feeds valence-shell: none`. "None" is an acceptable answer. Omitting the line is not.
. *Label `feeds:valence-shell`* (repo-local by D206; not in the canonical labels.yml, per its rule 4). It exists in every feeder and in valence-shell as of 2026-09-30, on 90 issues. Apply it to issues whose acceptance criteria change a valence-shell frontier item.
. *The standing umbrella is valence-shell#210* ("Theory feed: feeder progress toward valence-shell"). It holds one checklist row per NW item above and links each labelled feeder issue.
. *The valence-shell side of the contract is D-3.* Each entry in `docs/PROOF-OPEN-FRONTIER.adoc` gains a `Feeder:` field naming the repo and module expected to discharge or inform it. A frontier item with no feeder is either valence-shell-internal or a gap to raise with the owner.
. *Progress is judged at mechanisation, not at documentation.* A feeder link moves from C to D when a bridge doc exists. It moves to M only when a valence-shell proof file imports the feeder module *and* that file builds in CI.
. Provenance and registries go in `.k9` / `.deed`. Never register feeder provenance in A2ML files; see <<caveats>>.
