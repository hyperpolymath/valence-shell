* *Measured*: a command was run or a file read in this session (2026-11-17).

== 0. Bottom line

. *As a shell it is not usable today.* On 112 everyday command lines it gives
  the same result as bash on 57. `dash`, a minimal POSIX shell, gives the same
  result on 91, and brush, an existing shell written in Rust, on 111. The
  failures are ordinary: `[ -d / ]` always fails; a quoted `*` or `[` reaches
  programs with a backslash added; `cat *.txt` is not expanded; `mkdir -p a/b`
  creates a directory named `-p`; `exit 7` exits with 0; a nested `for` loop
  gives the wrong answer. Several of these report success. All of them are on
  `main` and predate this month's branches (Measured, section 2).
. *The tests did not see it, and neither does the plan.* No test file on `main`
  runs the built program; they call its functions. The plan's definition of done
  (gates G1 to G11) has no gate for use as a shell, so "v1.0-honest" could ship
  with every one of these failures (Measured, sections 2.6 and 8.1).
. *What is distinctive does work.* The history with proof references, the dry
  run, checkpoints, transactions, undo and redo all behave as described in an
  interactive session, and the two open pull requests add a crash-safe journal
  and handle-based containment (Measured, section 2.7).
. *Undo reaches very little of a real session.* It covers the shell's own file
  commands, redirections and variables. An edit in an editor, `sed -i`, `git`,
  a build: none of it can be undone. This limits usefulness more than any gap
  in the language (Measured, section 3).
. *There is a product here, and it is not "another bash".* Nothing in wide use
  gives undo and redo, with grouping, for the effects of arbitrary commands.
  The nearest tool, `try`, shows the mechanism works, and an experiment in this
  session reproduced it at about 4.5 ms per command (sections 4.2 and 7.4).
. *Recommended direction:* treat the engine as the product and the shell
  language as one of several front ends, built last. In order: a command-line
  tool and library; a plug-in for bash, zsh and fish; capture of any command;
  a server for AI agents; and only then an interactive shell of its own,
  probably on an existing core. Each step is a product someone can use. The
  other routes, their costs and the ratings are in sections 7 and 10.

=== 2.2 Root causes

Each was reproduced on the `main` build. "Silent" means the command reports
success and the result is wrong.

[cols="1,5,4,1",options="header"]
|===
|# |What happens |Example |Silent

|R1 |A quoted `*`, `?`, `[`, `{` or `~` is passed on with a backslash in front. The parser marks quoted characters with a backslash in a flat string (`quoted_word_to_string`, `parser.rs:2527`) and nothing takes it off again before the program is started |`grep '[0-9]' f` searches for `\[0-9]`. `awk '{print $1}'` is a syntax error. `pass:[echo "*"]` prints `pass:[\*]` |Yes
|R2 |Unquoted wildcards, braces and `~` are expanded only when the command also has a redirection. The plain path (`execute_external`) never calls the expansion; the redirection path does (`external.rs:41`) |`cat *.txt` fails with "No such file"; `cat *.txt > out` works |No
|R3 |`[ … ]` always fails. The parser removes the closing `]` (`parser.rs:3713`) and the evaluator then requires it (`test_command.rs:248`) |`[ -d / ] && echo yes` prints "test: missing ']'" |No
|R4 |Command substitution works only as the whole value of an assignment, and only for another program |`x=$(date +%Y)` works. `x=$(echo hi)`, `echo $(date)`, `for i in $(seq 3)` and backquotes do not |Partly
|R5 |Arithmetic expansion works only in an assignment |`pass:[i=$((i+1))]` works; `pass:[echo $((1+2))]` prints the text `pass:[$((1+2))]` |Yes
|R6 |`${x#p}`, `${x%p}` and `${x^^}` give an empty string. `$$` is not known |`x=abcdef; echo ${x#abc}` prints an empty line |Yes
|R7 |The file commands take one operand and no options. An option is treated as the operand; further operands are dropped |`mkdir -p a/b` creates a directory named `-p`. `touch a b c` creates `a`. `ls -la` is an error |Yes
|R8 |In `-c` and script mode, a failing built-in command ends the whole script |`ls nosuch; echo after` prints nothing after the error |No
|R9 |`exit N` exits with status 0. `set -e` has no effect. `! cmd`, `break`, `continue` and `wait` do not exist, so a loop that relies on `break` never ends. `&` is accepted only at the end of a line |`exit 7; echo $?` in the caller gives 0 |Partly
|R10 |`export` and `VAR=value cmd` do not reach the program being run |`export FOO=bar; sh -c 'echo $FOO'` prints an empty line |Yes
|R11 |A `for` loop inside a `for` loop runs the inner loop once with the outer variable empty |`for i in a b; do for j in 1 2; do echo $i$j; done; done` prints `1 2` |Yes
|R12 |Not supported: arrays, `pass:[(( ))]`, `let`, the C-style `for`, `[[ -d x ]] && …`, subshells, a brace group or a `while` loop in a pipeline, `read` from a here-string, `type`, `command -v`, `pushd` |`echo a b \| while read x y; do …` gives "Command not found: while" |No
|R13 |A redirection on a built-in command is resolved inside the session root |`ls nosuch 2>/dev/null` fails: "Parent directory does not exist: <root>/dev" |No
|R14 |After starting a program the shell polls for its exit every 50 ms (`external.rs:326`, and two more loops like it) |1,000 runs of `/bin/true` take 50.5 s on the journal build (100 runs take 5.1 s on `main`); bash takes 1.4 s for 1,000 |-
|===

R1 and R7 are the dangerous ones. They change what a command does without
saying so.

R1 to R6 share one cause. The POSIX shell turns a word into arguments in fixed
steps: tilde, parameter, command and arithmetic expansion, then field
splitting, then pathname expansion, then quote removal. Here the steps are
spread over the parser and three execution paths, and "was this character
quoted" is carried as backslashes inside a string. The root `CLAUDE.md` already
lists the consequence as its first priority ("requires quote-context
threading"). This cannot be patched into correctness one case at a time
(Inference); section 9.1 gives the structural answer.

`main` the root itself moves with `cd`, so `cd /etc; touch x` created `/etc/x`
during this review (removed afterwards). That is hole (f) of the route plan and
is closed on valence-shell#232.

made them about thirteen times faster than `main` on tmpfs, because `main`
rewrites its whole state file on every operation. Two costs stand out: R14
(50 ms on every program), and the price of recording every variable assignment
durably (on a real disk each record is a flush).

=== 2.7 What works well

The parts that carry the project's idea are the best-made parts (Measured):

* `explain rm f` shows the preconditions, the state change, the inverse and the
  theorem, and changes nothing.
* `checkpoint`, `diff` and `restore` name a state, show what separates it from
  now, and return to it.
* `begin`, `commit` and `rollback` group operations; on valence-shell#230
  rollback checks first and refuses rather than half-finishing.
* The journal on valence-shell#230 survives a crash at every point the harness
  can reach, and its model is proved in Agda.
* On valence-shell#232, thirteen of the fifteen known runtime holes are closed.

Three things in the product's own output say more than the proof ledger allows,
and should be reworded whatever else is decided:

* `replay` and `diff` print "all proven reversible ✓" and "All reversals proven".
  The theorems are about the model; the link from the model to this code is
  `tested-only` in the ledger. One of the theorems named, for variables, is
  listed in `history --proofs` as "pending".
* `proofs` prints "✓ Zig FFI layer checks preconditions". That layer is not
  connected to the shell.
* `obliterate` describes its three overwrites as "NIST SP 800-88 Purge". In
  that standard, overwriting with ordinary write commands is the *Clear* level;
  Purge needs device commands or cryptographic erase (Reported: section 5.3).

== 3. What undo covers in a real session

Undo covers what the shell does itself: `mkdir`, `rmdir`, `touch`, `rm`, `cp`,
`mv`, `ln -s`, `chmod`, `chown`, output redirection and variable assignment.
Measured in an interactive session and with `-c`:

[cols="4,4",options="header"]
|===
|Action |`undo` afterwards

|`touch t`, `rm t`, `mv a b` |Reversed
|Edit and save a file in `vim` |"Nothing to undo"
|`sed -i s/a/X/ f` |Not reversed; `undo` goes to the operation before it
|`git init` |"Nothing to undo"
|`echo hi > f` on `main` and the journal branch |Fails: "Undo touch failed: No such file or directory". Fixed on valence-shell#232 (the redirection records a path relative to the root)
|A file changed by another program since the operation |`undo` overwrites the other program's data (hole b, still open: section 10, decision 4)
|===

In ordinary work most changes to files are made by other programs: editors,
version control, build tools, package managers, `sed`, `tar`. So the feature the
project is named for applies to a small share of what a user does, and only if
they type the plain form of a handful of commands (section 2.3).

Two further limits follow from recording everything durably:

* The previous value of an overwritten variable is written to the state file
  (Measured: after `T=first; T=second` the file holds `first`). A secret held
  in a variable therefore reaches the disk. The file is mode 0600 on the
  journal branch and 0644 on `main`.
* Contents of removed and overwritten files are kept in the same file until
  step C4 of the route plan moves them to a store of their own.

== 4. What this is

=== 4.1 Three things in one repository

. *An engine for reversible operations*: operations with inverses, a history,
  transactions, checkpoints, a journal, containment, and deliberate
  irreversible deletion with a record. About 9,400 lines. Sound in outline,
  with known holes being closed.
. *A proof corpus about a model of that engine*: Agda as the source, rechecked
  in Lean and Coq. Sound for the model. Not connected to the code by anything
  mechanical.
. *A shell interpreter wrapped round the engine*: about half the Rust. It is
  the weakest part, the largest part, and the part the roadmap spends most of
  its words on ("v0.10.x POSIX coverage").

The first two are what make the project different. The third is what a user
meets first.

=== 4.2 What is new here and what is not

Reported unless marked; links in section 5.3.

[cols="2,5,4",options="header"]
|===
|Feature |Already available elsewhere |Not available elsewhere

|Undo |Deleted files (`trash-cli`, `gio trash`). Whole volumes back to a snapshot (snapper on btrfs, ZFS, NILFS2). One command inspected before it is applied (`try`). Files an AI agent changed with its own editing tool (agent checkpoints) |Undo and redo of the effects of arbitrary commands, one command at a time, with grouping. No mainstream shell has undo
|Containment |Landlock, bubblewrap, firejail, nsjail, systemd settings: mature, and they wrap any shell |Nothing: this is a property the product must have, not a reason to choose it
|Record of what was done |`auditd`, `sudo` session logs, `tlog`, Teleport; sealing in journald and in transparency logs |A record that ties each command to the changes it made and can show it was not altered
|Deletion with evidence |Device commands (`nvme sanitize`, `blkdiscard --secure`), cryptographic erase |Nothing reliable for a single file on flash or copy-on-write storage, and software cannot change that
|Proofs |Smoosh (a tested semantics of the POSIX shell, not proved); CoLiS (a core calculus proved, the translation trusted) |No machine-checked shell exists. Proofs about the operations, as here, are a smaller target and a reachable one
|===

Two signals from that history deserve weight:

* Microsoft withdrew file-system transactions twice for lack of use:
  Transactional NTFS ("extremely limited developer interest") and the
  transaction cmdlets in PowerShell ("very limited usage"). Transactions that
  developers have to ask for were not wanted (Reported).
* `try` won a best-paper award at OSDI in 2026 (Reported, checked), and every
  AI coding agent's documentation says its rewind does not cover what shell
  commands did (Reported; checked for one of them). Undo that needs no
  cooperation from the command is wanted now.

=== 4.3 The jobs it could do

[cols="1,4,4,3",options="header"]
|===
|# |Job |What people use today |What it would take

|J1 |"I am about to do something risky to this directory tree and want to be able to take it back exactly" |Copy the directory first; git, if it is a repository; a snapshot, if the file system has them |Undo for any command, in the shell they already use, at no noticeable cost
|J2 |"An AI agent is about to run commands in my project. I want it confined, I want to see what it changed, and I want one step back" |Containers and sandboxes (isolate, do not undo); git; agent checkpoints (their own edits only) |The same engine behind a tool interface for agents
|J3 |"I must be able to show what was done, and what was deleted" |`sudo` logs, `auditd`, ticket systems, device erase certificates |A sealed record, and deletion methods that match the storage
|J4 |"I study or teach reversible computing and verified systems" |Papers |The model, the proofs and a small demonstrator
|===

None of the four needs a new shell language. J1 and J2 need coverage of
arbitrary commands and low friction. J3 needs integrity of the record. J4 needs
the proofs. A new interpreter is a way of delivering them, and it is the most
expensive way.

=== 4.4 A statement of identity to rule on

Proposed for the project's deed once the owner has ruled. Until then it is a
proposal and no descriptive file is changed.

*IS:* an environment for accountable operations on a directory tree. Every
change it makes is either reversible, with a machine-checked account of why the
reversal is right, or deliberately irreversible, with a durable record that it
happened. Shells, scripts and agents are ways of reaching it.

*IS NOT:* a replacement for bash; a POSIX shell; a sandbox for hostile code; a
backup system; a compliance product; a proof that a storage device forgot
anything.

*The name still fits:* a valence shell is the outer layer through which an atom
bonds. Here it is the layer through which a tree is changed.

=== 5.2 Modularity

What "modular like oh-my-zsh" needs from a shell: a start-up file; a way to
read other files; functions and aliases; hook functions that run before and
after each command; a completion interface; a prompt the user can define. A
plug-in is then a file that uses those, and a theme is a prompt definition.

valence-shell has the second and third (`source`, functions, aliases) and none
of the rest (Measured, section 2.4). So a plug-in system *for* this shell is
not possible today, and building one would mean building most of what makes an
interactive shell first.

The other direction needs nothing from this shell's interpreter: deliver
`undo`, `redo`, transactions and the engine's file commands *as a plug-in for*
bash, zsh and fish. The host shell supplies the language, the completion, the
prompt and the user's existing configuration. That is stage S2.

The engine is modular in a different sense that matters more: section 8.4
splits it into a core, capture, the record, and front ends behind one
interface.

An NGS-like direction is still open later, without a new parser: a typed
scripting layer over the engine in a language the estate already has
(section 11).

== 9. Types, logics and proofs that give a more final answer

=== 9.1 Words that know what was quoted

R1 to R6 exist because quoting is stored as backslashes in strings. The
structural fix is a word type: a word is a list of segments, each marked quoted
or not. Expansion produces fields. Only unquoted segments are split and matched
against file names. Arguments are built from fields, and no escape character
exists inside the program at all, so the fault of R1 cannot be written.

One property covers the class: for every byte string `s`, the argument that a
program receives for the quoted form of `s` is `s`. It is a property test
today and a short lemma over the word type later. This matters only if an
interpreter of our own is kept.

=== 9.2 Change sets with footprints

An operation's effect is a set of changes; each change gives a path, what was
there before and what is there after (kind, metadata, content hash). The
inverse swaps before and after. A change set may be applied only when every
path it names is in its "before" state.

* *One theorem instead of eleven:* applying the inverse after the change set
  returns the tree, given that precondition. `mkdir` and `rmdir`, write and
  restore, move and move back are instances.
* *Hole (b) is answered by construction:* an undo whose paths no longer match
  what the operation left is not applicable, so it is refused. Nothing needs to
  be remembered to check.
* *Paths outside the set are untouched* (the frame rule of separation logic),
  so changes made elsewhere by other programs never invalidate an undo.
* *Two change sets on disjoint paths commute* (as in the patch theories of
  Darcs and Pijul), so an earlier operation can be undone without undoing the
  later ones when they do not overlap. No shell or snapshot tool offers that.
* The built-in commands and the captured effects of any program become the same
  thing, which is what makes stage S3 an extension and not a second engine.

In the estate's own vocabulary, the "before" half of a change set is the echo
of a lossy map: the witness needed to go back. That reading stays
documentation only, as the bridge rules require.

=== 9.3 Authority only by handle

valence-shell#232 gives the built-in commands a handle on the session root and
no other way to reach files. The remaining step in the plan, a ban on ambient
file calls outside one module, turns a convention into something the compiler
checks. For other programs the same idea is Landlock together with the
overlay.

=== 9.4 A one-use permit for what cannot be undone

Obliteration is refused inside a transaction by a run-time check. A permit
value that cannot be copied, issued by the confirmation and consumed by the
operation, makes "irreversible operations happen only with a fresh, explicit
permit" something the type checker enforces. Rust's ownership expresses it
directly. It is also the natural meeting point with the estate's affine types.

=== 9.5 A chained record

Each entry of the record carries the hash of the one before, and checkpoints
are signed. That makes edits and reordering detectable. It does not show that
entries were not cut from the end; a copy of the latest hash held somewhere
else does. The model-level lemma is small. The real questions are where the
keys and that copy live, and they are the owner's.

=== 9.6 Ratchets

The battery, the hole list and the proof manifest are the same device: a list
that may only shrink, checked by a machine. Every stage gate in section 8 has
that form.

== Appendix B. The runner

Usage: `runner.sh <work-dir> <shell-under-test> <battery-file> <result-file>`.
The shell under test is called as `<shell> -r <dir> -c <line>`; for dash and
brush a two-line wrapper drops the first two arguments. Battery lines have the
form `group|command line`.

[source,bash]
----
#!/usr/bin/env bash
# Compare everyday shell snippets under bash and vsh. No file is removed.
S="$1"; V="$2"; LIST="$3"; OUT="$4"
export NO_COLOR=1 RUST_BACKTRACE=0
: > "$OUT"
norm() { sed -e 's/\x1b\[[0-9;]*m//g' -e '/^\[op:[0-9a-f]*\]/d' -e '/^\[txn:[0-9a-f]*\]/d'; }
run_one() {
  local cat="$1" snip="$2" d1 d2 bo br vo vr verr st
  d1=$(mktemp -d -p "$S/work"); d2=$(mktemp -d -p "$S/work")
  bo=$(cd "$d1" && timeout 10 bash -c "$snip" 2>/dev/null </dev/null); br=$?
  vo=$(cd "$d2" && timeout 10 "$V" -r "$d2" -c "$snip" 2>"$d2/.err" </dev/null | norm)
  d3=$(mktemp -d -p "$S/work")
  (cd "$d3" && timeout 10 "$V" -r "$d3" -c "$snip" >/dev/null 2>&1 </dev/null); vr=$?
  verr=$(head -c 160 "$d2/.err" | tr '\n\t' '  ')
  if [ "$bo" = "$vo" ] && [ "$br" = "$vr" ]; then st=PASS; elif [ "$bo" = "$vo" ]; then st=RC; else st=FAIL; fi
  printf '%s\t%s\t%s\t%s\t%s\t%s\t%s\t%s\n' "$st" "$cat" "$(printf "%s" "$snip" | tr "\n\t" "~ ")" "$br" "$(printf '%s' "$bo" | head -c 50 | tr '\n\t' '~ ')" "$vr" "$(printf '%s' "$vo" | head -c 50 | tr '\n\t' '~ ')" "$verr" >> "$OUT"
}
mkdir -p "$S/work"
while IFS= read -r line; do
  [ -z "$line" ] && continue
  cat="${line%%|*}"; snip="${line#*|}"
  run_one "$cat" "$snip"
done < "$LIST"
run_one redir "$(printf 'cat <<EOF2\nheredoc $((1+1))\nEOF2')"
