== Core Claims & Evidence

=== Claim 1: "794 tests passing, 0 failures — ~478 theorem candidates across 6 proof systems"

**From README**: the test count and the theorem-candidate count are separate
claims, and the second is a count of *candidates*, not of proved theorems.

**Evidence**:
`impl/rust-cli/` is where the tests live (`cargo test --all-features`); the
proof trees are `proofs/{coq,lean4,agda,idris2,isabelle,mizar,z3}/`. The Coq
tree alone declares 133 `Theorem`/`Lemma` commands and contains no
`admit`/`Admitted`.

**Caveat** — the status of every obligation is recorded in the
<<proof-ledger,Proof Ledger>> below, and the two claims must not be merged. A
test suite result is `tested-only`. A theorem in a proof assistant is `proven`
*for the abstract model*. Nothing in this repository is `proven` about the Rust
code, and no percentage is quoted for that correspondence: it is `argued` plus
`tested-only` (see the ledger's model→code rows).

=== Claim 2: "Formally proven reversibility: `rmdir(mkdir(p, fs)) = fs`"

**From README**: the theorem holds under stated preconditions.

**Evidence**: `proofs/coq/filesystem_model.v:207`
(`mkdir_rmdir_reversible`), with the same property restated in
`proofs/lean4/FilesystemModel.lean`, `proofs/agda/FilesystemModel.agda`,
`proofs/isabelle/`, `proofs/mizar/` and `proofs/z3/`. The composition lemma is
`proofs/coq/filesystem_composition.v:352` (`operation_sequence_reversible`).

**Caveat**: this is a theorem about an abstract `Filesystem` function, not about
POSIX. The Rust CLI calls `libc`; whether that code refines the model is the
open correspondence row in the ledger — argued and tested, never proved.

=== Claim 3: "Advanced research prototype (v0.9.0) — not production-ready"

See <<_status,Status>>. This claim is accurate and is the one the repository
wants readers to take away.

*Reading rule:* a row may only be as strong as the weakest step it depends on.
A theorem about the model is `proven` *for the model*; the link from model to
code is its own row, and it is `argued` here. Nothing in this ledger is
grade 1 or grade 2ii.

*Provenance of these rows (2026-11-01).* When this ledger was first written no
proof assistant was installed, so no row had been re-run. **Agda and Z3 have since
been installed and re-run** (see `docs/audits/2026-11-01-assurance-boundary-audit.adoc`,

installed in that environment, so **those rows still record the repository's own
evidence** and name, in the checker column, the invocation a future audit must

== Architectural Bridge

Valence Shell does not stand alone. It sits in a three-layer architecture:

* **Valence Shell** (this repo) — shell operations, history, undo/redo, in-model reversibility proofs.
* **`hyperpolymath/echo-types`** — semantic theory of structured loss; names what is recoverable, constrained, or genuinely lost.
* **`hyperpolymath/ochrance`** — receipt + attestation substrate (A2ML manifests, Merkle-backed state commitments, repair witnesses).

The bridge is **documentation-and-orientation-only**, not a mechanised dependency. See link:docs/ECHO-TYPES-OCHRANCE-BRIDGE.adoc[ECHO-TYPES-OCHRANCE-BRIDGE.adoc] for the canonical forbidden-moves list (no claiming production-readiness, mechanised Lean→Rust correspondence, RMO/GDPR beyond stubs, or Ochrance cryptographic integrity).

== Status

**Honest Assessment**: advanced research prototype; not production-ready. The
model→code correspondence is **the critical blocker** for any production claim,
and it is `argued`, not `proven` (see <<proof-ledger,Proof Ledger>>).

**What works**:
- Functional shell: 794 tests passing, interactive REPL working
- 133 Coq theorems plus restatements in five further systems, all about
  abstract models; every obligation's status is a ledger row
- Reversibility tracking: undo/redo functional for modelled operations
- Most POSIX features: pipes, redirections, glob, job control, variables

**What is not established**:
- No `proven` correspondence between the model and the Rust CLI (Creusot
  contracts do not exist here); the status is `argued` + `tested-only`
- No shell functions (`func() { ... }`) or script execution of `.sh` files
- RMO: `obliterate` is implemented as best-effort overwrite + unlink + an
  unsigned residue; no key provisioning, no anchor, no GDPR determination
- POSIX coverage is a subset
